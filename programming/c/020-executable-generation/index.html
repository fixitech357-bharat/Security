Memory Layout

Where Sections Live at Runtime

Once loaded, the executable's sections are mapped into the process's virtual memory in a specific order. This is the classic "memory layout of a C program."

Stack
Local variables and function calls. Grows downward.
high addresses ↓
Heap
Dynamically allocated memory (malloc, calloc). Grows upward.
↑ grows up
.bss
Uninitialized global and static variables. Zero-filled at load.
zero-filled
.data
Initialized global and static variables.
read + write
.rodata
Read-only data: string literals, constants.
read-only
.text
Machine code — the actual instructions. Read-only + executable.
low addresses ↑
🔍
Try it yourself: On Linux, run size ./program to see the byte sizes of text, data, and bss. Or use readelf -S ./program to list every section.
File Formats

Common Executable Formats

Different operating systems use different executable formats. They all do the same thing — just with slightly different internal layouts.

🐧
ELF
Executable and Linkable Format. Used by Linux, BSD, Solaris, and most Unix systems. Also used for object files and shared libraries.
libc.so.6
🪟
PE
Portable Executable. Used by Windows for .exe, .dll, and .sys files. Derived from COFF.
program.exe
🍎
Mach-O
Mach Object. Used by macOS and iOS. Handles executables, shared libraries, and object files with a flexible segment layout.
program.app
📀
a.out
The original Unix format (1970s). Simple but limited. Replaced by ELF on nearly all modern systems.
a.out (legacy)

Recap

What You Just Learned

An executable is not a black box — it is a structured file with clearly defined parts. Here's the summary:

ELF / PE / Mach-O
Every OS has its own executable format. They all serve the same purpose.
Sections Inside
.text (code), .data (init globals), .bss (zero globals), .rodata (constants).
The Loader
The OS kernel reads the ELF header, maps sections into memory, and jumps to _start.
_start → main
The real entry is _start, which sets up and then calls main().
