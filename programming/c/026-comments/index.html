The Two Styles

Single-line vs Multi-line Comments

C gives you two ways to write comments. Click each card to see how it works in practice.

📝
Single-line Comment
// This is a comment
Starts with // and continues to the end of the line. Everything after // on that line is ignored by the compiler.
Added in C99
📄
Multi-line Comment
/* This spans multiple lines */
Starts with /* and ends with */. Can span any number of lines. The original C comment style — available since C89.
Since C89
💡
Rule of thumb: Use // for short explanations on a single line. Use /* */ for block comments, file headers, and temporarily disabling chunks of code.

Rules & Pitfalls

Common Mistakes with Comments

Comments are simple, but they have a few rules that surprise beginners. Here are the most important ones:

🚫
No Nesting /* */
Multi-line comments do not nest. The first */ closes the comment — even if it appears inside another one.
/* outer /* inner */ still in comment? NO — already closed */
⚠️
// Inside /* */
A // inside a /* */ comment is just text. It does NOT start a new comment.
/* This // is fine and continues */ int x = 5;
📝
Comments in Strings
// and /* */ inside a string literal are NOT comments — they are part of the string.
printf("This is // a string"); /* prints: This is // a string */
🔓
Unclosed Comment
If you open /* and never close it, the compiler reads to the end of the file looking for */ and reports an error.
/* forgot to close int x = 5; // everything after is swallowed
✂️
Disabling Code
You can use comments to temporarily disable code. But be careful with /* */ — it can't wrap existing /* */ comments.
// printf("debug 1\n"); // printf("debug 2\n"); int y = 10;
💬
No Space Requirement
Comments don't need a space after //. And /* */ can be inline with code.
int x = 5;/* yes */ //no space needed either x = 10;
Best Practices

How to Write Good Comments

Comments are meant to explain why, not what. Here are the guidelines professional programmers follow:

🎯Explain Why, Not What

Don't repeat the code. Explain why the code does something unusual, why a workaround exists, or what business rule it implements.

📌Comment the Tricky Parts

Most code is obvious. Reserve comments for the 10% that needs explanation — algorithms, workarounds, non-obvious edge cases.

🔄Keep Them Updated

An outdated comment is worse than no comment. If you change the code, change the comment. Always.

📖Use File Headers

Start each file with a block comment describing its purpose, author, and license. This helps anyone opening the file for the first time.

🚫Don't Over-Comment

Too many obvious comments — like // increment x above x++; — clutter the code and reduce readability.

🧹Remove Dead Comments

Commented-out code is often left behind for years. If it's really dead, delete it. Version control remembers everything.

What You Just Learned

Comments are the easiest topic in C — but the most important habit to build. Here's the summary:

Two Styles
// for one line, /* */ for many.
Preprocessor Removes Them
Comments are gone before the compiler sees your code. Zero cost at runtime.
No Nesting
/* */ does not nest. The first */ closes the comment.
